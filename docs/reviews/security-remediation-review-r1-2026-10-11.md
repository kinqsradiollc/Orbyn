## SR-R1 — P1: key retirement races the supported rolling upgrade

**Locations:** `backend/src/lib/rewrap-secrets.ts:78–80`; `scripts/deploy.sh:299–302` and `:362–374`; Kubernetes migration Job sequencing in `deploy/k8s/migrate-job.yaml`.

The new migration rewraps currently observed `d1:` ciphertext and deletes `app_secrets.credentials_key`. The normal deployment pauses only the measurer/notifier before migration. Old API, AI and assistant processes continue serving until their later rolling replacements, and the script deliberately starts new replicas alongside old ones. On the exact legacy installation this upgrade targets, those old processes still have an empty SECRETS_KEY and may have cached the database key.

**Failing sequence:** old API/AI caches key K; migration converts a credential table or cached maintenance results and deletes K; an old process writes another `d1:` value using cached K after that table/result scan or after commit; replacement processes know only the external key. They cannot decrypt the late value. A process without a cached key can instead recreate a database key, undoing the intended separation. Old replicas can also fail to read newly rewrapped `v1:` data before they receive the new environment. Transactional conversion and its advisory lock do not serialize legacy writers, which do not acquire that lock. A Kubernetes PreSync migration before old pods stop has the same exposure.

**Builder correction:** Make the one-time legacy-key transition an explicit quiesced cutover, or a compatible staged migration. For quiescing, stop/drain all old credential/cached-output writers and prevent restart before conversion; ensure every required process receives the same validated external key before serving again. For staging, retain the old key until legacy writers are fenced, perform a final conversion/verification, then retire it. Define fail/retry/rollback behavior without restarting old keyless replicas over converted data. Do not rely on a post-migration restart note while the supported script continues a rolling upgrade. Preserve restrictive backup permissions and explain that pre-transition backups still contain the old key.

**Tester verification:** A disposable upgrade fixture must model a legacy writer with K cached, including a write after the converter has visited that store. Demonstrate either that the write is fenced or that final conversion retains decryptability; assert no residual `d1:` values or recreated database key before retirement. Cover provider column, SMTP JSON and maintenance-result JSON, interrupted conversion/retry, malformed ciphertext rollback, and the deployment ordering that enforces quiescence. No production deployment is requested.

This keeps ledger group F / `csf_855f85888987d9eaf7995613` open for upgrade acceptance. Requiring an external key for new production writes is sound; the remaining problem is transition safety.
