# Status and handoffs

Use current source and current task evidence. Historical reports may explain a
previous decision; they do not prove today's process, deployment or test status.

Read the current request/handoff, git state and relevant evidence before reporting.
If a process matters, inspect its known handle. Do not start tests, contact another
chat, edit product code or initiate visual work merely to prepare a status update.

A useful report names the scope, current phase, completed work, remaining work,
next action and evidence. Use a small table only when several stages need comparison.
Do not invent percentages, ETAs, acceptance or deployment from implementation.

Distinguish local edits, candidate commit, verification, independent review when
requested, remote push, merge and production deployment. Mark unverified facts
with their source date and limitation. One completed subtask does not complete
its parent. Record exclusions as excluded, not passed.

For handoffs include checkout/branch/revision or dirty diff, file/fixture ownership,
commands and results, unresolved findings, next action, and applicable user scope
or pause. For independent review cycles, preserve the round counter and the
[three-round limit](delivery.md#independent-qualification-when-requested).
Do not manufacture a review cycle when none was requested.
